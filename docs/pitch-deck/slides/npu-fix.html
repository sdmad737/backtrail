Technical ingenuity

The NPU did not work out of the box. Four fixes got the whole loop onto it.

1 · Three root causes, one dependency

No Tensor dispatch driver in the APK; the sample driver was built for an older runtime (“Unsupported dispatch runtime version”); the manifest lacked uses-native-library libedgetpu_litert.so (“Failed to initialize SB”). Fix: litert-npu-runtime-google-tensor 2.3.0 plus uncompressed JNI packaging. Upgrading LiteRT-LM alone did nothing.

2 · Forced JSON, 0% → 100% usable

Stock Gemma wrapped every answer in Markdown code fences, so our strict validator rejected all of them. Constraining decoding to a JSON schema in the runtime took usable answers from 0 of 66 to 66 of 66, with no retries.

3 · One engine, kept loaded

The bootstrap reloaded the 2.6 GB model for every photo: 20.8 s on first load. Now one engine stays resident; follow-up requests pay 0 ms to load. Both Gemma and EmbeddingGemma share the NPU at about 1.6 GB total.

4 · A cancel bug that broke the next request

In LiteRT-LM 0.18.0, cancelling a finished conversation corrupted the reused engine (“Failed to get num packed bytes”). We cancel only work that stopped early, and refuse overlapping requests instead of queueing them, so the UI never waits on an uninterruptible native call.

Each fix is a commit on main with the before and after measurement. Reproduction commands in the appendix.

This is the “how deep did you go” slide for engineers. Say the first one in full: three different error messages, three layers (APK, runtime version, manifest), one correct dependency. Then the JSON point in one line: the model was fine; the format was the bug. Thirty seconds total.
